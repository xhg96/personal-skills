# AGENTS.md — 规格即源码（Spec-as-Source）开发规范

> 本文件是本仓库所有 AI 编码 agent 的最高工作准则。开始任何任务前必须完整阅读并遵守。
> 若与其他指令冲突，以人类在当前会话中的明确指令为准，其次为本文件。

---

## 1. 设计背景

在 Vibe Coding 模式下，代码由 AI 生成，人类不再逐行阅读和维护代码。这带来两个问题：

1. **人类的决定容易丢失**：人类在对话中提出的需求和约束，散落在聊天记录里，下一次会话或换一个 agent 就没人记得了。
2. **人类无法掌控系统**：不读代码，就不知道自己提过的要求有没有被实现，也不知道 agent 在其余部分做了什么。

本规范的解决思路是：每个目录用两份自然语言文档代替代码，作为人类理解系统的入口。

| 文件 | 记录什么 | 约束力 |
|------|---------|-------|
| **spec.md** | **所有**经人类提出或确认过的实现 | **必须严格遵守** |
| **unspec.md** | **所有**未经人类确认的实现（即 agent 自行决定的部分） | 不约束后续修改，但必须如实反映当前代码 |

两份文件按"是否经人类确认"划分，**互不重叠、合起来完整**：本目录的每一项实现，要么在 spec.md 中，要么在 unspec.md 中，不能两边都没有。

- 读 spec.md，人类知道哪些是自己定下的、系统**必须**满足什么。
- 读 unspec.md，人类知道其余部分 agent 是怎么做的，不需要读代码。
- 人类确认 unspec.md 中的某一项后，它就从 unspec.md 移到 spec.md。

**复现标准**：即使删除全部代码，

- 凭 spec.md + unspec.md，能重建出与当前实现行为等价的系统；
- 只凭 spec.md，能重建出满足全部人类要求的系统（未确认部分可以不同）。

## 2. 核心原则

| # | 原则 | 含义 |
|---|------|------|
| P1 | **规格即约束** | spec.md 中的要求是代码必须遵守的事实来源；代码与之冲突时，以 spec.md 为准。 |
| P2 | **按确认划分** | 经人类确认的实现写进 spec.md；所有未经确认的实现写进 unspec.md。两者互不重叠，合起来覆盖本目录的全部实现。 |
| P3 | **一目录两文件** | 每个受管目录都必须同时有 spec.md 和 unspec.md。 |
| P4 | **就近描述** | 两份文件都只关心**当前目录**；子目录和其他目录通过超链接引用，不重复描述。 |
| P5 | **以对话为准** | 已记录进 spec.md 的必须严格遵守；未记录的由 agent 自由发挥，并且全部写进 unspec.md。 |
| P6 | **先记录后实现** | 人类提出新要求时，先写进 spec.md，再改代码。 |
| P7 | **持续一致** | 代码必须满足 spec.md；unspec.md 必须如实描述代码。每次任务结束前都要校验。 |
| P8 | **简短完整** | 两份文件都要用尽量短的篇幅、清晰的结构完整表达内容（见第 6 节）。 |

## 3. 覆盖范围

### 3.1 必须包含 spec.md 和 unspec.md 的目录

除 3.2 列出的例外外，**所有目录**都必须同时有这两份文件，包括根目录、源码、测试、脚本、配置、静态资源目录，以及只包含子目录的目录。

人类从未对某个目录提出过要求时，它的 spec.md 仍须存在，约束和验收标准写"暂无"即可。

### 3.2 例外（无需这两份文件）

- 版本控制与工具目录：`.git/`、`.idea/`、`.vscode/`
- 依赖与构建产物：`node_modules/`、`vendor/`、`.venv/`、`__pycache__/`、`dist/`、`build/`、`target/`、`coverage/`
- 根目录 `.specignore` 文件中列出的路径（语法同 `.gitignore`）

### 3.3 文件命名

- 文件名固定为小写 `spec.md` 和 `unspec.md`，与它们描述的代码放在同一目录。
- 每个目录各只能有一份。

## 4. 文件结构

### 4.1 spec.md（人类确认的要求）

```markdown
# <目录名> · spec

> 上级：[../spec.md](../spec.md) ｜ 实现说明：[unspec.md](./unspec.md)

## 约束
- C1：……（2026-11-15）
- C2：……
（没有则写"暂无"。约束较多时按主题用小标题分组。）

## 验收标准
- Given ……，When ……，Then ……
（没有则写"暂无"）

## 子目录
- [parser/](./parser/spec.md)
- [storage/](./storage/spec.md)
（没有子目录时省略本节）
```

说明：

- 头部链接和"子目录"列表只用于导航，不属于约束内容，由 agent 维护。
- 除导航外，spec.md 中的每一个字都必须来自人类的提出或确认。
- 人类对目录职责、边界、目录划分有明确要求时，写进"约束"一节。

### 4.2 unspec.md（agent 的实现说明）

```markdown
# <目录名> · unspec

> 上级：[../unspec.md](../unspec.md) ｜ 约束：[spec.md](./spec.md)
> 一句话职责：……

## 目录内容
| 名称 | 说明 |
|------|------|
| `xxx.ts` | …… |
| [`parser/`](./parser/unspec.md) | …… |

## 实现说明
覆盖本目录中所有未经人类确认的实现。本目录不涉及的小节直接省略：
- **对外接口**：名称、签名、参数与返回、错误
- **数据结构**：类型、字段、格式
- **核心流程**：关键步骤、算法、分支条件、重要常量
- **错误处理与边界条件**
- **依赖**：内部依赖（附链接）、外部库及版本
- **配置**：环境变量、配置项
- **设计取舍**：为什么这样做
```

说明：

- **完整覆盖**：本目录中任何未经人类确认的实现，都必须写进 unspec.md。判断方法：删除本目录代码后，凭 spec.md + unspec.md 能否重建出行为等价的代码；不能，就说明 unspec.md 有遗漏。
- **不重叠**：已经写进 spec.md 的内容，unspec.md 不再重复。
- **不矛盾**：unspec.md 不得与 spec.md 冲突。
- **如实**：unspec.md 描述的是当前代码的真实状态，代码改了，unspec.md 同步更新。
- **不逐行翻译**：写的是"做什么、按什么规则做"，不是代码本身。局部变量名、代码格式这类不影响行为和结构的写法细节不需要记录。

### 4.3 根目录的特殊内容

- **根目录 spec.md**：在"约束"中记录适用于整个仓库的人类要求，如技术栈、编码约定、禁止事项。人类描述过系统定位的，也记在这里。
- **根目录 unspec.md**：写系统概述、顶层模块总览（每个模块链接到其 unspec.md）、未被约束的技术栈选择，以及构建、运行、测试的命令。

## 5. 记录标准

### 5.1 什么写进 spec.md

人类在对话中表达的、关于系统**应该怎样**的任何决定，例如：

- 功能需求："导出要支持 CSV 和 Excel"
- 接口约定："这个函数就叫 `parseOrder`，返回值里要有 `total`"
- 技术选型："用 PostgreSQL，不要用 MySQL"
- 行为细节："超时时间设 30 秒"、"列表按创建时间倒序"
- 否定性要求："不要引入新的第三方依赖"
- 对 agent 方案的确认：agent 提出方案或人类读了 unspec.md 后回复"可以""就这样"，该方案即视为人类确认

### 5.2 什么写进 unspec.md

**除 spec.md 已记录的内容外，本目录的全部实现**，包括：

- agent 自行决定的接口设计、数据结构、算法、错误处理、依赖库、配置、目录划分等
- 人类明确表示"随便""你看着办"的部分的具体实现
- 人类的要求写得宽泛时（如"要快"），agent 选择的具体做法

### 5.3 什么都不写

- 讨论过程中被否决或被后续决定覆盖的方案
- 修改历史（留给 git）

### 5.4 写入 spec.md 的方式

1. **忠实原意**：按人类的原意记录，不扩大、不缩小、不擅自补充细节。人类说"要快"，就记"要快"，不要改写成"响应时间 < 100ms"。
2. **一条一事**：一条约束表达一个要求，便于逐条核对。
3. **注明日期**：建议在每条后注明日期，便于追溯。
4. **放对位置**：只涉及某个目录的约束，记在该目录；跨多个目录的要求，记在它们共同的上级目录（通常是根目录）。
5. **覆盖而非堆积**：新决定与旧约束冲突时，修改或删除旧约束，不要两条并存。

### 5.5 在两份文件之间转移内容

- **人类认可** unspec.md 中的某项选择 → 把它移入 spec.md 的约束，并从 unspec.md 删除。
- **人类否决** unspec.md 中的某项选择并给出要求 → 把要求写进 spec.md，修改代码，并同步更新 unspec.md。
- **人类撤销**某条约束（"这个无所谓了"）→ 从 spec.md 删除；对应实现若保留，改记在 unspec.md。

### 5.6 约束的解释

- 约束写得宽泛时（如"要快"），agent 在满足字面要求的范围内自由选择实现，并把具体选择写进 unspec.md。
- 约束有明显歧义、不同理解会导致实质不同的结果时，**向人类确认**，并把结论更新进 spec.md。
- 不得以"约束没写细"为由，违背约束的明显本意。

## 6. 可读性要求

两份文件都是给人读的。目标是：**人类花一两分钟就能读完一份文件，并准确掌握其内容。**

**结构**

- 优先用表格、列表和编号，不写大段散文。
- 条目较多时，按主题用小标题分组。
- 没有内容的可选小节直接省略；spec.md 的"约束"和"验收标准"没有内容时只写一行"暂无"。
- 篇幅没有硬性上限，以"尽量简短"为目标，但前提是内容完整。文件写得很长时，先检查是否有冗余、重复，或写进了不属于本目录的内容；如果都没有，长一些也没关系。

**语言**

- 一句话能说清的，不写成一段；一条约束只写一行。
- spec.md 中用"必须""不得""应"等明确的词，不用"尽量""最好"之类含糊的表达，除非人类的原话就是如此。
- 用陈述句写当前状态，不写背景故事、讨论过程和修改历史。
- 删掉没有信息量的句子，如"本模块非常重要""以下是详细说明"。
- 同一个概念在全仓库用同一个词。

**不重复**

- 同一条内容在全仓库只写一次，其他地方链接引用。
- 不复述上级目录、子目录或另一份文件（spec.md / unspec.md）中已有的内容。

**简短不等于省略**

- 精简的是表达方式，不是内容本身。人类提出的每一个要求都必须完整、准确地保留。
- 无法在不丢失原意的情况下再缩短时，以完整为准。

**持续整理**

- 每次更新时，顺手合并重复条目、删除过时内容、调整分组，避免文件随时间变得冗长杂乱。

## 7. 引用与链接规则

1. **只写本目录**：两份文件都只关心当前目录。子目录只给出链接（unspec.md 中可附一句话说明）。
2. **两棵链接树**：spec.md 之间、unspec.md 之间各自形成从根目录出发的链接树。每份文件头部链接到上级的同名文件（根目录除外），上级文件列出并链接到每个子目录的同名文件。
3. **同目录互链**：spec.md 与 unspec.md 在头部互相链接。
4. **使用相对路径**：如 `[parser](./parser/spec.md)`，不使用绝对路径或外部 URL。
5. **引用而非复制**：涉及其他目录或另一份文件的内容时，链接过去，不要复制。
   例：`C3：订单写入必须通过 [storage](../storage/spec.md) 完成。`
6. **无死链**：移动、重命名、删除目录时，必须同步修复所有指向它的链接。

## 8. Agent 工作流程

### 8.1 开始任何任务前

1. 从根目录沿链接逐级阅读到要修改的目录，读 spec.md 和 unspec.md，以及相关依赖目录的这两份文件。
2. 明确本次修改必须遵守哪些约束（含上级目录的全局约束）。
3. 通过 unspec.md 了解现有实现，必要时再读代码。

### 8.2 人类在对话中提出新要求

1. **记录**：按第 5 节，把要求写进对应目录的 spec.md。与已有约束冲突时，更新旧约束。
2. **实现**：修改代码，满足新要求，且不破坏其他约束。
3. **更新 unspec.md**：把本次自行做出的实现选择如实写进 unspec.md。
4. **校验**：执行 8.6 的一致性检查。

> 如果人类只是让你修个 bug 或做个小调整，且没有表达新的规则性要求，就不需要改 spec.md；但代码仍须满足所有约束，unspec.md 仍须同步更新。

### 8.3 人类直接修改了 spec.md 或 unspec.md

- **改了 spec.md**：视为需求，修改代码使其满足新约束，并同步更新 unspec.md。
- **改了 unspec.md**：视为人类对实现的要求。向人类确认是否要固化为约束：是，则移入 spec.md；否，则按修改后的 unspec.md 调整代码。

### 8.4 新建、移动、删除目录

- **新建**：在同一次提交中创建该目录的 spec.md 和 unspec.md，并在上级两份文件中添加链接。
- **移动或重命名**：同步更新两份文件的头部链接，以及全仓库所有指向它的链接；约束随之迁移。
- **删除**：从上级两份文件中移除该条目，清理所有指向它的链接。若被删除目录的 spec.md 中有约束，先向人类确认这些约束是作废还是迁移到别处。

### 8.5 冲突与不确定的处理

- **代码违反 spec.md**：修改代码。
- **unspec.md 与代码不符**：更新 unspec.md，使其如实反映代码。
- **unspec.md 与 spec.md 矛盾**：以 spec.md 为准，修改代码和 unspec.md。
- **约束之间互相矛盾，或某条约束无法实现**：停下来向人类报告，不要擅自取舍。
- **新要求与旧约束冲突，但人类没有明确说要覆盖**：向人类确认后再更新。
- **目录缺少这两份文件**：先补写。unspec.md 可以根据现有代码编写；spec.md 只写导航，约束写"暂无"。**不得根据代码反推约束**，代码的现状不等于人类的决定。

### 8.6 任务结束前的一致性检查（必须执行）

- [ ] 本次对话中人类提出的新要求，都已记录进对应的 spec.md
- [ ] spec.md 中没有混入人类未提出或未确认过的内容
- [ ] 本次涉及目录（含上级目录）的每一条约束，代码都满足
- [ ] 验收标准有对应的测试，且测试全部通过
- [ ] 本次涉及目录中所有未经人类确认的实现，都已写进 unspec.md（反向校验：只读代码复述实现，逐项确认在 spec.md 或 unspec.md 中能找到）
- [ ] unspec.md 如实反映修改后的代码，不与 spec.md 矛盾，也不重复 spec.md 的内容
- [ ] 本次涉及的每个目录都有两份文件，链接完整，没有死链
- [ ] 本次修改过的文件符合第 6 节可读性要求

可用以下命令快速检查缺失文件的目录（按需调整排除项）：

```bash
find . -type d \
  \( -name .git -o -name node_modules -o -name dist -o -name build \
     -o -name .venv -o -name __pycache__ -o -name vendor -o -name target \) -prune \
  -o -type d -print | while read -r d; do
    [ -f "$d/spec.md" ]   || echo "缺少 spec.md:   $d"
    [ -f "$d/unspec.md" ] || echo "缺少 unspec.md: $d"
  done
```

## 9. 从文档复现系统

当需要从零重建（代码丢失、换技术栈、重写模块）时，按需选择方式：

| 方式 | 依据 | 结果 |
|------|------|------|
| **按现状重建** | spec.md + unspec.md | 与当前实现行为等价 |
| **按约束重建** | 只读 spec.md | 满足全部人类要求，未确认部分自由实现 |

无论哪种方式：

1. 从根目录开始，沿链接逐个目录实现。
2. spec.md 中的约束和验收标准必须全部满足。
3. 重建完成后，按新代码更新 unspec.md。

---

## 10. 代码文件约定

- 每个源码文件顶部加一行注释，例如：
  `// 约束：./spec.md ｜ 实现说明：./unspec.md`
- 代码注释只解释局部实现细节，不重复两份文档中已有的内容。

---

## 11. 禁止事项

- ❌ 人类提出的要求没有记录进 spec.md
- ❌ 在 spec.md 中写入人类没有提出或确认过的内容
- ❌ 记录时扩大、缩小或擅自细化人类的原意
- ❌ 写出违反 spec.md 中任何约束的代码
- ❌ 有未经人类确认的实现，没有写进 unspec.md
- ❌ 改了代码却不更新 unspec.md
- ❌ 根据代码反推约束写进 spec.md
- ❌ 新建目录而不创建 spec.md 和 unspec.md
- ❌ 在一份文件中详细描述其他目录，或在多处重复同一内容
- ❌ 约束冲突或无法实现时擅自取舍，而不报告
- ❌ 在文档中写背景故事、讨论过程、修改历史或没有信息量的句子
- ❌ 为了简短而删减或改变人类要求的原意
- ❌ 留下死链

---

## 12. 人类的角色

在本规范下，人类：

- **对话**：像平常一样和 agent 交流需求，agent 负责把其中的决定记录进 spec.md；
- **阅读 spec.md**：了解自己做过哪些决定、系统必须满足什么；
- **阅读 unspec.md**：了解 agent 实际怎么实现的，不需要读代码；
- **认可或否决** unspec.md 中的选择，把满意的固化为约束，把不满意的改掉；
- **裁决** agent 报告的约束冲突和歧义；
- **评审** 时重点看 spec.md 的变更，确认记录的确实是自己的意思；再浏览 unspec.md 的变更，了解实现有何变化。
